# L2 - Detailed Requirements

Each L2 traces to exactly one L1. Every acceptance criterion is written in Given–When–Then form. Criteria describing the tool's behaviour are realisable as integration tests; the engineering-process criteria under L1-009 and L1-010 are proved instead by the build and by the continuous-integration run, because the codebase does not test its own shape.

**Reference vocabulary used throughout:**

- **Commands:** `primer init`, `primer check`, `primer mcp list`, `primer mcp check`, `primer mcp install`
- **Global options:** `--path <dir>`, `--verbosity <quiet|minimal|normal|detailed|diagnostic>`, `--format <text|json>`, `--no-color`, `--dry-run`, `--yes`
- **Exit codes:** `0` success · `1` unexpected failure · `2` usage or parse error · `3` configuration or validation error · `4` verification failed (drift detected, or required components missing)

---

## L2-001: Package as an installable .NET tool
**Traces to:** L1-001

The `Primer` project must produce a NuGet package flagged as a .NET tool with the command name `primer`, installable globally or as a local tool manifest entry.

**Acceptance Criteria:**
1. Given the solution at a clean checkout, when `dotnet pack -c Release` is run, then a `.nupkg` is produced whose nuspec declares a package type of `DotnetTool` and a tool command named `primer`.
2. Given the produced package, when it is installed with `dotnet tool install --global --add-source <dir> Primer`, then invoking `primer --version` from an unrelated working directory exits `0` and writes a version string to stdout.
3. Given the produced package, when it is installed as a local tool against a tool manifest, then `dotnet primer --version` exits `0`.
4. Given the package metadata, when it is inspected, then package id, description, repository URL, licence expression, and target framework are all populated and non-empty.

## L2-002: Report version and build provenance
**Traces to:** L1-001

The tool must report a Semantic Versioning 2.0.0 informational version that identifies the exact build.

**Acceptance Criteria:**
1. Given an installed tool, when `primer --version` is run, then stdout contains a version matching `^\d+\.\d+\.\d+(-[0-9A-Za-z.-]+)?(\+[0-9A-Za-z.-]+)?$` and the process exits `0`.
2. Given an installed tool, when `primer --version --format json` is run, then stdout is a single JSON object containing `version` and `commit` properties.
3. Given `primer --version` is run twice from the same installed build, when the two outputs are compared, then they are byte-identical.

---

## L2-003: Root command help and discoverability
**Traces to:** L1-002

Invoking the tool without arguments, or with `--help` at any level, must render help that lists every available command and option.

**Acceptance Criteria:**
1. Given an installed tool, when `primer` is run with no arguments, then help text listing the commands `init`, `check`, and `mcp` is written to stdout and the process exits `0`.
2. Given an installed tool, when `primer --help` is run, then every global option (`--path`, `--verbosity`, `--format`, `--no-color`, `--dry-run`, `--yes`) appears in the output with a non-empty description.
3. Given an installed tool, when `primer init --help` is run, then every option specific to `init` appears with a non-empty description and the process exits `0`.
4. Given an installed tool, when `primer mcp --help` is run, then the subcommands `list`, `check`, and `install` are listed and the process exits `0`.

---

## L2-004: Exit-code contract
**Traces to:** L1-002

The tool must return exit codes according to a fixed contract so that scripts and CI can branch on the outcome.

**Acceptance Criteria:**
1. Given a valid repository, when `primer init` completes successfully, then the process exits `0`.
2. Given any command line containing an unrecognised option, when the tool is run, then a parse error is written to stderr and the process exits `2`.
3. Given a configuration file containing an invalid value, when any command is run, then a validation error naming the offending key is written to stderr and the process exits `3`.
4. Given a repository whose generated files are out of date, when `primer check` is run, then the process exits `4`.
5. Given an operation that throws an unhandled exception, when the tool is run, then the process exits `1` and no stack trace appears on stdout.

---

## L2-005: Global option vocabulary
**Traces to:** L1-002

Every global option must be accepted by every command with identical semantics.

**Acceptance Criteria:**
1. Given each of the commands `init`, `check`, `mcp list`, `mcp check`, and `mcp install`, when each is invoked with `--path <dir>`, then the command operates against `<dir>` rather than the current working directory.
2. Given `--path` pointing at a non-existent directory, when any command is run, then an error naming the path is written to stderr and the process exits `3`.
3. Given `--format json` on any command, when the command completes, then stdout parses as a single valid JSON document and contains no human-oriented prose lines.
4. Given `--verbosity quiet`, when a command completes successfully, then stdout and stderr are both empty and the exit code alone conveys the outcome.

---

## L2-006: Unrecognised commands and options are rejected helpfully
**Traces to:** L1-002

Mistyped input must fail fast with a suggestion rather than silently doing nothing.

**Acceptance Criteria:**
1. Given the command line `primer inti`, when the tool is run, then stderr contains a message naming `inti` as unrecognised and suggesting `init`, and the process exits `2`.
2. Given the command line `primer init --agnet claude`, when the tool is run, then stderr names the unrecognised option and the process exits `2`.
3. Given any parse failure, when the tool is run, then no file in the target repository is created, modified, or deleted.

---

## L2-007: Repository root discovery
**Traces to:** L1-003

The tool must resolve the repository root by walking upward from the target path to the nearest directory containing a `.git` entry.

**Acceptance Criteria:**
1. Given a git repository with a nested directory `src/Primer/Commands`, when any command is run with `--path src/Primer/Commands`, then the resolved repository root is the directory containing `.git`.
2. Given a directory that has no `.git` entry in itself or any ancestor, when `primer init` is run, then stderr states that no repository root was found and the process exits `3`.
3. Given a git worktree whose `.git` is a file rather than a directory, when `primer init` is run, then the repository root is resolved successfully and the process exits `0`.
4. Given a resolved repository root, when `--format json` is used, then the output includes the absolute resolved root path.

---

## L2-008: Technology stack detection
**Traces to:** L1-003

The tool must identify the languages, frameworks, package managers, and test frameworks in use from marker files present in the repository.

**Acceptance Criteria:**
1. Given a repository containing a `.sln` and one or more `.csproj` files, when `primer init --dry-run --format json` is run, then the detected stack includes `dotnet` and lists the discovered project files by repository-relative path.
2. Given a repository containing `package.json`, when detection runs, then the detected stack includes `node` and names the package manager implied by the present lock file (`package-lock.json` to npm, `pnpm-lock.yaml` to pnpm, `yarn.lock` to yarn).
3. Given a repository containing a `.csproj` that references the `xunit` package, when detection runs, then the detected test framework is reported as `xunit`.
4. Given a repository containing no recognised marker file, when detection runs, then the detected stack is reported as empty and the command still exits `0`.
5. Given a repository containing markers for more than one stack, when detection runs, then every detected stack is reported and none is silently discarded.

## L2-009: Build, test, and lint command inference
**Traces to:** L1-003

Inferred commands must be exact and runnable, including the flags needed for reproducibility, never a bare tool name.

**Acceptance Criteria:**
1. Given a repository whose root contains `Primer.sln`, when command inference runs, then the inferred build command is `dotnet build Primer.sln -c Release` and the inferred test command is `dotnet test Primer.sln -c Release`, each naming the actual solution file found.
2. Given a repository with a `package.json` whose `scripts` object defines `test` and `lint`, when command inference runs, then the inferred commands invoke those scripts through the detected package manager.
3. Given a repository where no test command can be inferred, when generation runs, then the generated file omits the test command rather than emitting a placeholder such as `<your test command>`.
4. Given any inferred command, when it is emitted into a generated file, then every file path it references exists in the repository at generation time.

---

## L2-010: Project structure summarisation
**Traces to:** L1-003

Structure discovery must respect ignore rules and stay bounded.

**Acceptance Criteria:**
1. Given a repository with a `.gitignore` excluding `bin/` and `obj/`, when structure discovery runs, then no path under `bin/` or `obj/` appears in the discovered structure.
2. Given a repository containing a directory nested deeper than the configured maximum depth (default 4), when structure discovery runs, then traversal stops at the maximum depth and deeper paths are absent from the output.
3. Given a repository containing more files than the configured file-count cap (default 50,000), when discovery runs, then discovery halts at the cap, a warning is written to stderr, and the process still exits `0`.
4. Given a repository containing a symbolic link that points to an ancestor directory, when discovery runs, then traversal terminates without infinite recursion.

---

## L2-011: Existing convention detection
**Traces to:** L1-003

The tool must detect and reuse the engineering conventions the repository already declares rather than inventing new ones.

**Acceptance Criteria:**
1. Given a repository containing `.editorconfig`, when detection runs, then that file is recorded as the authoritative formatting source and referenced by its repository-relative path in generated output.
2. Given a repository containing `Directory.Build.props`, when detection runs, then it is recorded among the discovered convention files.
3. Given a repository containing workflow files under `.github/workflows/`, when detection runs, then the build and test commands those workflows execute are preferred over inferred defaults.
4. Given a repository containing none of the recognised convention files, when detection runs, then the corresponding sections are omitted from generated output and the process exits `0`.

---

## L2-012: Analysis reads only safe, bounded content
**Traces to:** L1-003

Repository analysis must not read content it does not need, and must not stall on files it cannot usefully parse.

**Acceptance Criteria:**
1. Given a repository containing a file larger than the configured per-file read cap (default 1 MiB), when analysis runs, then that file's content is not read into memory and the file is reported only by name and size.
2. Given a repository containing a binary file, when analysis runs, then the file's content is not parsed as text and no binary content appears in any generated file or log.
3. Given a repository containing a path ignored by `.gitignore`, when analysis runs, then that path's content is not read.
4. Given a repository containing a file the process lacks permission to read, when analysis runs, then a warning naming the path is written to stderr and the command continues to completion.

## L2-013: Generate AGENTS.md at the repository root
**Traces to:** L1-004

`primer init` must write an `AGENTS.md` file at the repository root containing the sections that established AGENTS.md practice prescribes, populated from the discovered repository context.

**Acceptance Criteria:**
1. Given a repository with no `AGENTS.md`, when `primer init` is run, then `AGENTS.md` exists at the repository root and the process exits `0`.
2. Given a generated `AGENTS.md`, when it is inspected, then it contains, in order, the headings `Project Overview`, `Commands`, `Project Structure`, `Testing`, `Code Style`, `Git Workflow`, and `Boundaries`.
3. Given a repository where a given section has no discovered content, when generation runs, then that section is omitted entirely rather than emitted with placeholder text.
4. Given a generated `AGENTS.md`, when it is parsed as Markdown, then it contains no unresolved template tokens (no occurrence of `{{` or `}}`).

---

## L2-014: AGENTS.md stays concise
**Traces to:** L1-004

Generated guidance must stay short enough to be read in full by an agent, per the 150-line guidance.

**Acceptance Criteria:**
1. Given any generated `AGENTS.md`, when its lines are counted, then the total is 150 or fewer.
2. Given a repository large enough that full content would exceed 150 lines, when generation runs, then lower-priority content is truncated, a note pointing to the fuller source is emitted, and the file still ends at or below 150 lines.
3. Given a generated `AGENTS.md`, when it is inspected, then it contains no section whose body restates the section heading without adding information.

---

## L2-015: Generated content is exact and grounded
**Traces to:** L1-004

Every command and path emitted by repository analysis must be real, exact, and verifiable against the repository. These criteria govern analysis mode. Greenfield generation names the folders a project is about to create, none of which exist yet, and is governed by L2-065 and L2-066 instead.

**Acceptance Criteria:**
1. Given an `AGENTS.md` generated by repository analysis, when every repository-relative path it names is checked, then each of those paths exists in the repository.
2. Given an `AGENTS.md` generated by repository analysis, when every command it names is checked, then each command includes the flags required to run it reproducibly and none is a bare tool name such as `dotnet` or `npm`.
3. Given a repository where a fact cannot be derived from repository content, when generation runs, then that fact is omitted and no speculative or invented statement is emitted in its place.

---

## L2-016: Boundaries section declares what agents must not modify
**Traces to:** L1-004

Generated guidance must state explicitly which paths are off limits.

**Acceptance Criteria:**
1. Given a repository containing generated or vendored directories, when `primer init` is run, then the `Boundaries` section of `AGENTS.md` names those paths as never to be modified.
2. Given a repository containing a lock file, when generation runs, then the `Boundaries` section states that the lock file is modified only through its package manager.
3. Given a generated `AGENTS.md`, when the `Boundaries` section is inspected, then it names `AGENTS.md` itself as generated and states the command that regenerates it.

---

## L2-017: Hierarchical AGENTS.md for multi-project repositories
**Traces to:** L1-004

For repositories containing multiple distinct projects, the tool must be able to emit nested per-directory guidance in addition to the root file.

**Acceptance Criteria:**
1. Given a repository containing two or more independent projects and the option `--recursive`, when `primer init --recursive` is run, then an `AGENTS.md` is written at the root and one in each detected project directory.
2. Given a nested `AGENTS.md`, when it is inspected, then it contains only guidance specific to its directory and does not repeat the root file's content.
3. Given a repository containing a single project, when `primer init --recursive` is run, then only the root `AGENTS.md` is written.
4. Given `primer init` without `--recursive`, when it is run on a multi-project repository, then only the root `AGENTS.md` is written.

---

## L2-018: Generated files are plain Markdown
**Traces to:** L1-004

A generated file must carry nothing but the guidance it exists to deliver.

**Acceptance Criteria:**
1. Given any `AGENTS.md` written by `primer init`, when it is inspected, then it contains no HTML comment, no `primer:` delimiter, and no line recording the generating tool version or a content hash of its inputs.
2. Given two consecutive runs against an unchanged repository, when the two generated `AGENTS.md` files are compared, then they are byte-identical.

---

## L2-019: CLAUDE.md links to AGENTS.md without duplicating it
**Traces to:** L1-005

`CLAUDE.md` must be a bare pointer. A Markdown link is insufficient, because it only references the guidance rather than delivering it; Claude Code's `@` import directive resolves `AGENTS.md` into context at load time, so an agent reading `CLAUDE.md` alone obtains the complete guidance with nothing duplicated. The generated file carries the import directive and nothing else.

**Acceptance Criteria:**
1. Given a repository with no `CLAUDE.md`, when `primer init` is run, then `CLAUDE.md` exists at the repository root and its only non-empty line is the import directive `@AGENTS.md`.
2. Given a generated `CLAUDE.md` whose `AGENTS.md` states a fact not present anywhere in `CLAUDE.md`, when a Claude Code session loads `CLAUDE.md`, then that fact is present in the resulting context.
3. Given a generated `CLAUDE.md`, when the import target is resolved from the repository root, then `AGENTS.md` exists at that path.
4. Given a generated `CLAUDE.md`, when its bytes are inspected, then the file ends with exactly one trailing newline.
5. Given a generated `CLAUDE.md` and its `AGENTS.md`, when the two are compared, then no heading present in `AGENTS.md` appears in `CLAUDE.md`.

---

## L2-020: Agent selection option
**Traces to:** L1-005

The `--agent` option must narrow which tool-specific files are written, and must be repeatable. Absent it, a run writes the instruction file for every supported agent: an agent file nobody asked for costs one small pointer, whereas an agent file nobody wrote costs a tool its guidance entirely.

**Acceptance Criteria:**
1. Given `primer init` with no `--agent` option, when it is run, then the instruction file for every supported agent is written — `AGENTS.md`, `CLAUDE.md`, `GEMINI.md`, and `.github/copilot-instructions.md` — and no other file is created.
2. Given `primer init --agent gemini --agent copilot`, when it is run, then `AGENTS.md` plus the Gemini and Copilot instruction files are written and `CLAUDE.md` is not created.
3. Given `primer init --agent all`, when it is run, then the instruction file for every supported agent is written.
4. Given `primer init --agent claude --agent claude`, when it is run, then `CLAUDE.md` is written once and the process exits `0`.

---

## L2-021: Per-agent file locations
**Traces to:** L1-005

Each supported agent's file must be written to that tool's conventional path.

**Acceptance Criteria:**
1. Given `--agent claude`, when generation runs, then the file is written to `CLAUDE.md` at the repository root.
2. Given `--agent gemini`, when generation runs, then the file is written to `GEMINI.md` at the repository root.
3. Given `--agent copilot`, when generation runs, then the file is written to `.github/copilot-instructions.md`, creating the `.github` directory if it does not exist.
4. Given `--agent codex`, when generation runs, then `AGENTS.md` is treated as the native Codex instruction file and no additional Codex-specific file is created.
5. Given any tool-specific file other than `AGENTS.md`, when it is inspected, then it references `AGENTS.md` by link or by import directive and does not restate its sections.
6. Given a target tool that supports an import or transclusion directive, when its instruction file is generated, then that directive is used so the tool loads `AGENTS.md` from the instruction file alone.
7. Given a target tool that supports no such directive, when its instruction file is generated, then the file instructs the agent to read `AGENTS.md` before proceeding and still does not restate its contents.

## L2-022: Unsupported agent values are rejected
**Traces to:** L1-005

**Acceptance Criteria:**
1. Given `primer init --agent notarealagent`, when it is run, then stderr names the unsupported value and lists every supported value, and the process exits `2`.
2. Given `primer init --agent notarealagent`, when it is run, then no file in the repository is created or modified.
3. Given `primer init --agent CLAUDE`, when it is run, then the value is matched case-insensitively and `CLAUDE.md` is written.

---

## L2-023: Dry-run previews without writing
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given a repository with no generated files, when `primer init --dry-run` is run, then the intended content of every file is written to stdout, no file is created on disk, and the process exits `0`.
2. Given a repository with existing generated files, when `primer init --dry-run` is run, then a unified diff of the intended change against the current file content is written to stdout and no file is modified.
3. Given `primer init --dry-run --format json`, when it is run, then stdout is a JSON document listing each target path with its intended action (`create`, `update`, or `unchanged`).
4. Given a repository where the generated content matches the existing content, when `primer init --dry-run` is run, then every target path is reported as `unchanged`.

---

## L2-024: Generated files are replaced on every run
**Traces to:** L1-006

Every file the tool writes is generated in full, so a run replaces what it finds rather than merging with it.

**Acceptance Criteria:**
1. Given an existing `AGENTS.md`, whatever its content and however it was authored, when `primer init` is run, then it is reported as `update` and replaced in full by generated content.
2. Given an existing `CLAUDE.md` whose content differs from the generated pointer, when `primer init` is run, then it is reported as `update` and replaced by the generated pointer.
3. Given an existing `CLAUDE.md` whose content already equals the generated pointer, when `primer init` is run, then it is reported as `unchanged` and its last-write timestamp is not updated.

---

## L2-025: Generation is idempotent
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given an unchanged repository, when `primer init` is run twice in succession, then the resulting files are byte-identical after the first and second runs.
2. Given an unchanged repository, when `primer init` is run a second time, then stdout reports every target path as `unchanged` and no file's last-write timestamp is updated.

---

## L2-026: Writes are atomic and encoding-stable
**Traces to:** L1-006

**Acceptance Criteria:**
1. Given any generated file, when its bytes are inspected, then the encoding is UTF-8 without a byte-order mark.
2. Given a repository whose `.gitattributes` or `.editorconfig` specifies a line ending, when generation runs, then the generated file uses that line ending; absent such a declaration, the file uses `LF`.
3. Given a write that fails partway through, when the failure occurs, then the original file content remains intact and no partial or zero-length file is left at the target path.
4. Given a generated file, when it is inspected, then it ends with exactly one trailing newline.

---

## L2-027: Verify generated files against the repository
**Traces to:** L1-006

`primer check` must detect drift without modifying anything.

**Acceptance Criteria:**
1. Given a repository whose generated files match what generation would currently produce, when `primer check` is run, then the process exits `0` and no file is modified.
2. Given a repository whose `AGENTS.md` no longer matches current generation output, when `primer check` is run, then the differing paths are reported and the process exits `4`.
3. Given a repository with no generated files at all, when `primer check` is run, then the missing paths are reported and the process exits `4`.
4. Given any invocation of `primer check`, when it completes, then no file in the repository has been created, modified, or deleted.

---

## L2-028: Declare required MCP components
**Traces to:** L1-007

The set of MCP servers a repository requires must be declared as data, not hard-coded, and must be listable.

**Acceptance Criteria:**
1. Given a repository with a Primer configuration declaring required MCP servers, when `primer mcp list` is run, then every declared server is listed with its name, version constraint, and install method.
2. Given a repository with no declared MCP requirements, when `primer mcp list` is run, then the tool's built-in defaults are listed and the process exits `0`.
3. Given a configuration declaring an MCP server with a missing required field, when any `mcp` command is run, then stderr names the offending entry and the process exits `3`.
4. Given `primer mcp list --format json`, when it is run, then stdout is a JSON array of objects each containing `name`, `version`, and `install` properties.

---

## L2-029: Detect installed MCP components
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given an agent client configuration file that registers a required MCP server, when `primer mcp check` is run, then that server is reported as installed together with the configuration file it was found in.
2. Given a required server registered at a version outside the declared constraint, when `primer mcp check` is run, then it is reported as outdated with both the found and required versions.
3. Given a required server absent from every known client configuration, when `primer mcp check` is run, then it is reported as missing.
4. Given an agent client configuration file that does not exist on the machine, when `primer mcp check` is run, then that client is reported as not configured and the command continues to check the remaining clients.
5. Given a malformed client configuration file, when `primer mcp check` is run, then the parse failure is reported with the file path, the file is left untouched, and the process exits `3`.

---

## L2-030: Report the MCP gap actionably
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given one or more missing or outdated required servers, when `primer mcp check` is run, then the process exits `4` and stdout names, for each, the exact remediation command to run.
2. Given every required server installed and in range, when `primer mcp check` is run, then the process exits `0`.
3. Given `primer mcp check --format json`, when it is run, then stdout is a JSON document reporting each server with a status of `installed`, `outdated`, or `missing`.

---

## L2-031: Installation requires explicit consent
**Traces to:** L1-007

Installation changes the developer's machine and must never happen implicitly.

**Acceptance Criteria:**
1. Given missing required servers and an interactive session, when `primer mcp install` is run, then the exact changes are displayed and confirmation is requested before any change is applied.
2. Given the confirmation prompt, when the operator declines, then no configuration file is modified and the process exits `0`.
3. Given a non-interactive session without `--yes`, when `primer mcp install` is run, then no change is applied, stderr states that `--yes` is required, and the process exits `3`.
4. Given `primer mcp install --dry-run`, when it is run, then the intended changes are printed and no configuration file is modified.
5. Given `primer init`, when it is run, then no MCP component is installed as a side effect.

---

## L2-032: Client configuration edits are surgical and reversible
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given a client configuration file containing unrelated entries, when `primer mcp install --yes` modifies it, then every unrelated entry is preserved with its original values.
2. Given a client configuration file, when it is modified, then a timestamped backup of the prior content is written before the change is applied and its path is reported.
3. Given a modified client configuration file, when it is parsed, then it is valid JSON and loads successfully in the target client.
4. Given a required server already present at an acceptable version, when `primer mcp install --yes` is run, then that entry is left unchanged and reported as already satisfied.

---

## L2-033: MCP operations degrade gracefully when offline
**Traces to:** L1-007

**Acceptance Criteria:**
1. Given no network connectivity, when `primer mcp check` is run, then locally-determinable status is still reported, network-dependent checks are reported as unknown, and the process exits `4` only if a required server is definitively missing.
2. Given a network request that does not complete within the configured timeout (default 10 seconds), when an `mcp` command is run, then the request is abandoned, a timeout is reported naming the endpoint, and the process exits `1`.
3. Given no network connectivity, when `primer init` is run, then generation completes normally and the process exits `0`.

---

## L2-034: Configuration precedence
**Traces to:** L1-008

**Acceptance Criteria:**
1. Given a setting defined only by built-in defaults, when a command is run, then the default value is used.
2. Given the same setting defined in a repository configuration file and by a built-in default, when a command is run, then the configuration file value is used.
3. Given the same setting defined in a configuration file and in a `PRIMER_`-prefixed environment variable, when a command is run, then the environment variable value is used.
4. Given the same setting defined in an environment variable and as a command-line argument, when a command is run, then the command-line value is used.
5. Given `--verbosity diagnostic`, when a command is run, then the effective value and originating source of each setting is written to stderr.

---

## L2-035: Options are validated at startup
**Traces to:** L1-008

**Acceptance Criteria:**
1. Given a configuration value that violates its declared constraint, when any command is run, then validation fails before any file is read or written, stderr names the offending key and constraint, and the process exits `3`.
2. Given a configuration file that is not valid JSON, when any command is run, then stderr names the file and the parse position, and the process exits `3`.
3. Given a configuration file containing an unrecognised key, when any command is run, then a warning naming the key is written to stderr and the process continues.
4. Given a valid configuration, when any command is run, then options are bound to strongly-typed classes registered through the options pattern.

---

## L2-036: Composition through dependency injection
**Traces to:** L1-008

**Acceptance Criteria:**
1. Given the application host, when it starts, then every command handler is resolved from the service container rather than constructed directly.
2. Given the service container, when it is built and validated at startup, then no service has an unresolvable dependency and no captive dependency is present.
3. Given a command handler under test, when a test substitutes the file-system and console abstractions in the container, then the handler executes with no real file-system or console access.

---

## L2-037: Template overrides
**Traces to:** L1-008

**Acceptance Criteria:**
1. Given a repository containing a template override file at the configured template path, when `primer init` is run, then the override is used in place of the built-in template for that file.
2. Given a template override referencing an unknown token, when `primer init` is run, then stderr names the unknown token and the process exits `3`.
